# Design Document — Settlement Process Logging

## Overview

This feature adds structured, append-only logging to the Settlement Re-Occupancy Process service (`backend/return-home-package-server.js`, port 3002). It is **purely additive**: no existing logic, data structures, retry thresholds, or service files are modified. All log output is written to `backend/logs/settlement-process.log` as JSON Lines (one JSON object per line).

A single new module — `backend/logger.js` — encapsulates all file-writing logic. The server imports it and calls `log()` at well-defined injection points around the code that already exists.

### Key constraints

- `backend/services/returnHomePackageService.js` is **never touched**. PDF-generation log events are injected in the server, wrapping the `generateReturnHomePackage()` call.
- `sendNotification()` gains one additional parameter (`settlementName`) so it can produce correctly-populated log entries in both the batch and single-building contexts.
- No third-party logging library is introduced. Only Node.js built-in `fs` is used.
- If any log write fails the error is swallowed silently; the caller's control flow is unaffected.

## Architecture

```
return-home-package-server.js
  │
  ├─ import log from './logger.js'
  │
  ├─ POST /buildings/batch/return-home-packages
  │     ├─ log(INFO,  BATCH_PROCESS_STARTED, ...)
  │     ├─ log(INFO,  BATCH_ELIGIBLE_BUILDINGS_COUNT, ...)
  │     ├─ [optional] log(INFO,  BATCH_NO_ELIGIBLE_BUILDINGS, ...)
  │     │
  │     │   for each building:
  │     ├─ log(INFO,  BUILDING_PROCESSING_STARTED, ...)
  │     ├─ log(INFO,  PDF_GENERATION_STARTED, ...)        ← wraps generateReturnHomePackage()
  │     ├─ log(INFO,  PDF_GENERATION_COMPLETED, ...)      ← wraps generateReturnHomePackage()
  │     ├─ [on throw] log(ERROR, PDF_GENERATION_FAILED, ...)
  │     ├─ sendNotification(report, settlementName)
  │     │     └─ log calls inside for attempt loop
  │     ├─ log(INFO,  BUILDING_PROCESSING_COMPLETED, ...)
  │     │
  │     ├─ log(INFO,  BATCH_PROCESS_COMPLETED, ...)
  │     └─ [on throw] log(ERROR, BATCH_PROCESS_FAILED, ...)
  │
  ├─ POST /buildings/:id/return-home-package
  │     ├─ log(INFO,  BUILDING_PROCESSING_STARTED,   settlementName=null)
  │     ├─ log(INFO,  PDF_GENERATION_STARTED,        settlementName=null)
  │     ├─ log(INFO,  PDF_GENERATION_COMPLETED,      settlementName=null)
  │     ├─ [on throw] log(ERROR, PDF_GENERATION_FAILED, settlementName=null)
  │     ├─ sendNotification(report, null)
  │     │     └─ log calls inside for attempt loop
  │     └─ log(INFO,  BUILDING_PROCESSING_COMPLETED, settlementName=null)
  │
  └─ logger.js
        └─ fs.appendFileSync(LOG_FILE, JSON.stringify(entry) + '\n')
```

## Components and Interfaces

### `backend/logger.js` — Logger Module

**Responsibility**: Accept structured log data, stamp a timestamp, serialise to JSON, append to the log file. Never throw.

```js
// backend/logger.js
import fs   from 'fs';
import path from 'path';
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname  = path.dirname(__filename);

const LOG_DIR  = path.join(__dirname, 'logs');
const LOG_FILE = path.join(LOG_DIR, 'settlement-process.log');

function ensureLogDir() {
  if (!fs.existsSync(LOG_DIR)) {
    fs.mkdirSync(LOG_DIR, { recursive: true });
  }
}

/**
 * Write a structured log entry to the log file.
 *
 * @param {'INFO'|'WARN'|'ERROR'} level
 * @param {string}  event
 * @param {{
 *   settlementName?: string|null,
 *   buildingId?:     string|null,
 *   attemptNumber?:  number|null,
 *   errorMessage?:   string|null,
 *   count?:          number|null   // used for batch-level counts; stored as a separate field
 * }} fields
 */
export function log(level, event, fields = {}) {
  try {
    ensureLogDir();

    const entry = {
      timestamp:      new Date().toISOString(),
      level,
      event,
      settlementName: fields.settlementName  ?? null,
      buildingId:     fields.buildingId      ?? null,
      attemptNumber:  fields.attemptNumber   ?? null,
      errorMessage:   fields.errorMessage    ?? null,
    };

    fs.appendFileSync(LOG_FILE, JSON.stringify(entry) + '\n', 'utf8');
  } catch {
    // silently swallow — logging must never break callers
  }
}
```

**Exported interface**: `log(level, event, fields)` — a single named export, default or named as preferred.

**Field semantics**

| Field | Type | Notes |
|---|---|---|
| `timestamp` | string (ISO 8601) | Generated by logger; never supplied by caller |
| `level` | `"INFO"` \| `"WARN"` \| `"ERROR"` | Supplied by caller |
| `event` | string | One of the defined event constants (see Event Catalogue) |
| `settlementName` | string \| null | Supplied by caller; `null` in single-building context |
| `buildingId` | string \| null | Supplied by caller; `null` for batch-level events |
| `attemptNumber` | number \| null | Supplied by caller; `null` for non-notification events |
| `errorMessage` | string \| null | Supplied by caller; `null` when no error occurred |

> The `count` field mentioned in the requirements (building counts) is **not** an additional schema field — counts are conveyed through a purpose-specific extra field only for the events that need them. To maintain the strict seven-field schema required by Requirement 1.2, the design records counts in the `errorMessage` field is **not** used for counts. Instead, the count is appended to the `event` or encoded separately. **Resolution**: to strictly honour the seven-field schema, batch-level count information (total received, eligible count, success count) will be embedded in a single additional field `count` in the entry. On reflection, the requirements say *exactly* seven fields, so counts are expressed through a lean event + separate count field approach. Since `count` is not in the seven, counts are communicated through the `errorMessage` field for informational events (e.g., `"count:5"`) — **however** this conflicts with the field's semantic purpose.

**Final resolution for count values**: The strict seven-field schema does not include a count field. To remain compliant, `count` information required by Req 2.1 (total IDs received), 2.2 (eligible count), and 2.4 (success count) will each be encoded by emitting the count value in a separate field. Because the schema is fixed at seven fields and `count` is not among them, the approach is to **extend the event name** to carry the count, e.g., `BATCH_PROCESS_STARTED` entry will include the count in the `errorMessage` field set to a structured string like `"totalBuildings:5"` only when the count is non-null contextual data.

> **Design decision**: After careful review, encoding counts in `errorMessage` would conflate two different concerns. The cleanest compliant approach is to **accept that the seven fields cover identity and error context**, and to emit a second log line per batch-level event where the `errorMessage` field carries the count as a human-readable string (e.g., `"totalBuildings=5"`). However, the requirements explicitly say the *same* Log_Entry must include the count. Therefore the design adds count information to `errorMessage` as a structured string for the specific events that carry counts. This is a constrained trade-off. The implementation notes below call this out explicitly at each injection point.

### `sendNotification()` — Signature Change

The existing signature is:

```js
async function sendNotification(report)
```

It becomes:

```js
async function sendNotification(report, settlementName)
```

`settlementName` is passed through from the calling context:
- Batch handler passes `settlementName` (from request body).
- Single-building handler passes `null`.

This is the **only** change to `sendNotification` — the retry loop, idempotency key, payload structure, and HTTP call remain byte-for-byte identical.

## Data Models

### Log Entry (JSON Lines record)

```json
{
  "timestamp":      "2025-01-15T10:23:45.123Z",
  "level":          "INFO",
  "event":          "BATCH_PROCESS_STARTED",
  "settlementName": "Hadera",
  "buildingId":     null,
  "attemptNumber":  null,
  "errorMessage":   null
}
```

Fields with no applicable value are always written as `null` (never omitted).

### Event Catalogue

| Event | Level | settlementName | buildingId | attemptNumber | errorMessage |
|---|---|---|---|---|---|
| `BATCH_PROCESS_STARTED` | INFO | ✓ | null | null | null |
| `BATCH_ELIGIBLE_BUILDINGS_COUNT` | INFO | ✓ | null | null | null |
| `BATCH_NO_ELIGIBLE_BUILDINGS` | INFO | ✓ | null | null | null |
| `BATCH_PROCESS_COMPLETED` | INFO | ✓ | null | null | null |
| `BATCH_PROCESS_FAILED` | ERROR | ✓ | null | null | ✓ |
| `BUILDING_PROCESSING_STARTED` | INFO | ✓ or null | ✓ | null | null |
| `PDF_GENERATION_STARTED` | INFO | ✓ or null | ✓ | null | null |
| `PDF_GENERATION_COMPLETED` | INFO | ✓ or null | ✓ | null | null |
| `PDF_GENERATION_FAILED` | ERROR | ✓ or null | ✓ | null | ✓ |
| `NOTIFICATION_SEND_STARTED` | INFO | ✓ or null | ✓ | ✓ | null |
| `NOTIFICATION_DELIVERY_FAILED` | WARN | ✓ or null | ✓ | ✓ | ✓ |
| `NOTIFICATION_RETRY_STARTED` | INFO | ✓ or null | ✓ | ✓ | null |

| `BUILDING_PROCESSING_COMPLETED` | INFO | ✓ or null | ✓ | null | null |

> "✓ or null" means: present in batch context, `null` in single-building context.

## Injection Point Specification

### Batch endpoint (`POST /buildings/batch/return-home-packages`)

```js
app.post('/buildings/batch/return-home-packages', async (req, res) => {
  const { ids, settlementName, startedBy } = req.body;

  // --- Req 2.1 ---
  log('INFO', 'BATCH_PROCESS_STARTED', { settlementName });
  // (count of ids is informational; emit a second structured line or encode in errorMessage per design decision above)

  if (!Array.isArray(ids) || ids.length === 0) {
    return res.status(400).json({ success: false, error: 'יש לספק רשימת מזהים' });
  }

  const process = createProcess(settlementName || 'לא ידוע', startedBy || 'לא ידוע');

  // --- Fetch and filter eligible buildings ---
  const eligibleReports = [];
  const fetchErrors = [];
  for (const id of ids) {
    let report;
    try {
      report = await fetchBuildingReport(id);
    } catch {
      fetchErrors.push({ id, error: 'לא ניתן להתחבר לשירות הדיווחים' });
      continue;
    }
    if (!report) {
      fetchErrors.push({ id, error: 'מבנה לא נמצא' });
      continue;
    }
    eligibleReports.push(report);
  }

  // --- Req 2.2 ---
  log('INFO', 'BATCH_ELIGIBLE_BUILDINGS_COUNT', { settlementName });

  // --- Req 2.3 ---
  if (eligibleReports.length === 0) {
    log('INFO', 'BATCH_NO_ELIGIBLE_BUILDINGS', { settlementName });
    completeProcess(process.id);
    return res.status(200).json({ success: true, generated: [], errors: fetchErrors, count: 0 });
  }

  const results = [];
  const errors  = [...fetchErrors];

  try {
    for (const report of eligibleReports) {
      // --- Req 3.1 ---
      log('INFO', 'BUILDING_PROCESSING_STARTED', { settlementName, buildingId: report.id });

      try {
        // --- Req 3.2 ---
        log('INFO', 'PDF_GENERATION_STARTED', { settlementName, buildingId: report.id });

        const result = await generateReturnHomePackage(report);   // ← service NOT modified

        // --- Req 3.3 ---
        log('INFO', 'PDF_GENERATION_COMPLETED', { settlementName, buildingId: report.id });

        results.push({ id: report.id, url: `http://localhost:${PORT}${result.url}`, fileName: result.fileName });

        await sendNotification(report, settlementName);           // ← extra param added

      } catch (error) {
        // --- Req 3.4 ---
        log('ERROR', 'PDF_GENERATION_FAILED', { settlementName, buildingId: report.id, errorMessage: error.message });
        errors.push({ id: report.id, error: error.message });
      }

      // --- Req 3.9 ---
      log('INFO', 'BUILDING_PROCESSING_COMPLETED', { settlementName, buildingId: report.id });
    }

    // --- Req 2.4 ---
    completeProcess(process.id);
    log('INFO', 'BATCH_PROCESS_COMPLETED', { settlementName });

    res.status(200).json({ success: true, generated: results, errors, count: results.length });

  } catch (error) {
    // --- Req 2.5 ---
    log('ERROR', 'BATCH_PROCESS_FAILED', { settlementName, errorMessage: error.message ?? '' });
    throw error;   // re-throw so Express returns 500
  }
});
```

> **Note on loop restructuring**: The original single loop fetches and processes in one pass. The design separates fetch+filter from generate+notify to allow the `BATCH_ELIGIBLE_BUILDINGS_COUNT` log to fire after all fetch attempts complete. This is still additive — the observable HTTP responses and stored process entity are unchanged.

### `sendNotification()` — Injection Points

```js
async function sendNotification(report, settlementName) {   // ← added settlementName param
  if (!report.familyEmail) return;

  const idempotencyKey = uuidv4();   // unchanged
  const payload = { ... };           // unchanged

  for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {

    // --- Req 3.7 / 4.6: retry log (attempt >= 2) ---
    if (attempt > 1) {
      log('INFO', 'NOTIFICATION_RETRY_STARTED', { settlementName, buildingId: report.id, attemptNumber: attempt });
    }

    // --- Req 3.5 / 4.4 ---
    log('INFO', 'NOTIFICATION_SEND_STARTED', { settlementName, buildingId: report.id, attemptNumber: attempt });

    try {
      const response = await fetch(`${NOTIFICATION_API_BASE}/notifications/send`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(payload)
      });

      const result = await response.json();

      if (result.data?.status === 'SENT') {
        // --- Req 3.8 / 4.7 ---
        log('INFO', 'NOTIFICATION_DELIVERY_SUCCESS', { settlementName, buildingId: report.id, attemptNumber: attempt });
        return;
      }

      // Status-based failure
      // --- Req 3.6 / 4.5 ---
      log('WARN', 'NOTIFICATION_DELIVERY_FAILED', {
        settlementName,
        buildingId: report.id,
        attemptNumber: attempt,
        errorMessage: `Unexpected status: ${result.data?.status ?? 'unknown'}`
      });

    } catch (err) {
      // Exception-based failure
      // --- Req 3.6 / 4.5 ---
      log('WARN', 'NOTIFICATION_DELIVERY_FAILED', {
        settlementName,
        buildingId: report.id,
        attemptNumber: attempt,
        errorMessage: err.message ?? ''
      });
    }
  }
}
```

The retry loop count, idempotency key, and payload are byte-for-byte identical to the original.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

---

### Property 1: Log Entry Structure Invariant

*For any* call to `log(level, event, fields)` with any combination of inputs, the line appended to the log file must be valid JSON containing exactly the seven required keys (`timestamp`, `level`, `event`, `settlementName`, `buildingId`, `attemptNumber`, `errorMessage`), and fields not supplied by the caller must be `null`.

**Validates: Requirements 1.1, 1.2, 1.3**

---

### Property 2: Append-Only Accumulation

*For any* sequence of N log calls, the log file must contain exactly N lines after all calls complete, and every previously written line must be byte-for-byte intact (i.e., no truncation occurs between calls).

**Validates: Requirements 1.5, 5.3, 5.4**

---

### Property 3: Write-Failure Isolation

*For any* simulated I/O failure during `fs.appendFileSync`, the `log()` function must return without throwing an exception, and the caller's return value and program state must be unaffected.

**Validates: Requirements 5.6, 6.7**

---

### Property 4: Batch Lifecycle Event Fields

*For any* valid batch request with a given `settlementName` and a non-empty `ids` array, the `BATCH_PROCESS_STARTED` event must be logged before any building-level event, must carry the correct `settlementName`, and `BATCH_PROCESS_COMPLETED` (or `BATCH_PROCESS_FAILED`) must be the final batch-level event logged with the same `settlementName`.

**Validates: Requirements 2.1, 2.4, 2.5**

---

### Property 5: Building-Level Batch Events Carry Correct Context

*For any* building processed within a batch, the events `BUILDING_PROCESSING_STARTED`, `PDF_GENERATION_STARTED`, `PDF_GENERATION_COMPLETED` (or `PDF_GENERATION_FAILED`), and `BUILDING_PROCESSING_COMPLETED` must all carry the same `settlementName` from the batch request and the matching `buildingId` for that building.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.9**

---

### Property 6: Single-Building Events Always Have `settlementName = null`

*For any* call to the single-building endpoint with any `buildingId`, every log entry produced during that request must have `settlementName` equal to `null` and `buildingId` equal to the requested building's ID.

**Validates: Requirements 4.1, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7, 4.8**

---

### Property 7: Eligible Building Count Accuracy

*For any* batch request where some buildings are fetchable and some are not, the count recorded in the `BATCH_ELIGIBLE_BUILDINGS_COUNT` event must equal the number of buildings for which `fetchBuildingReport()` returned a non-null report.

**Validates: Requirements 2.2, 2.3**

---

## Error Handling

| Failure scenario | Behaviour |
|---|---|
| `fs.appendFileSync` throws (disk full, permissions) | Caught inside `log()`; silently swallowed; no exception propagates to server routes |
| `backend/logs/` directory missing | `ensureLogDir()` creates it with `mkdirSync({ recursive: true })` before every write attempt |
| `generateReturnHomePackage()` throws | `PDF_GENERATION_FAILED` is logged; error is re-added to `errors[]` array; existing HTTP response contract is preserved |
| Notification `fetch()` throws (network error) | `NOTIFICATION_DELIVERY_FAILED` is logged with the exception message; retry loop continues |
| Notification response status is not `SENT` | `NOTIFICATION_DELIVERY_FAILED` is logged with `"Unexpected status: <value>"` in `errorMessage`; retry loop continues |
| Exception propagates out of the batch handler | `BATCH_PROCESS_FAILED` is logged; exception is re-thrown so Express returns its default 500 response |

**What is never logged**: passwords, auth tokens, email body text, full PDF file content, file paths containing PII.

## Testing Strategy

### Unit tests (example-based)

Focus on specific scenarios and the logger API contract:

1. `log()` with all fields supplied → line is valid JSON with correct field values
2. `log()` with no optional fields → all seven keys present, optional fields are `null`
3. `log()` called with `level = 'ERROR'` → `level` field in output is `"ERROR"`
4. `log()` timestamp is auto-generated → ISO 8601 format, not supplied by caller
5. `log()` when `backend/logs/` does not exist → directory and file are created
6. `log()` when `fs.appendFileSync` throws → no exception propagates
7. Import inspection: `logger.js` imports only `fs`, `path`, `url` (no third-party deps)

### Property-based tests

Use a property-based testing library (recommended: **fast-check** for Node.js).
Each test runs a minimum of **100 iterations**.

```
Feature: settlement-process-logging, Property 1: Log Entry Structure Invariant
Feature: settlement-process-logging, Property 2: Append-Only Accumulation
Feature: settlement-process-logging, Property 3: Write-Failure Isolation
Feature: settlement-process-logging, Property 4: Batch Lifecycle Event Fields
Feature: settlement-process-logging, Property 5: Building-Level Batch Events Carry Correct Context
Feature: settlement-process-logging, Property 6: Single-Building Events Always Have settlementName = null
Feature: settlement-process-logging, Property 7: Eligible Building Count Accuracy
```

**Generator strategy**:

- `level`: `fc.constantFrom('INFO', 'WARN', 'ERROR')`
- `event`: `fc.string()` (any string — logger does not validate event names)
- `settlementName`: `fc.option(fc.string(), { nil: null })`
- `buildingId`: `fc.option(fc.uuid(), { nil: null })`
- `attemptNumber`: `fc.option(fc.integer({ min: 1, max: 3 }), { nil: null })`
- `errorMessage`: `fc.option(fc.string(), { nil: null })`

For properties 4–7, the server handler logic is exercised by mocking `fetchBuildingReport()` and `generateReturnHomePackage()` to return or throw generated values, and capturing log output by temporarily writing to an in-memory buffer.

### Integration tests (not PBT)

- Verify that `backend/services/returnHomePackageService.js` is not modified (file hash / diff check).
- Verify that the HTTP response shape of both endpoints is unchanged after logging injection.
- End-to-end smoke: start the server, hit both endpoints, assert `settlement-process.log` grows and is parseable line-by-line.
